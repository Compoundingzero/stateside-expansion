# ELN submission service

`createSubmissionService({dbPath, setupToken, origin, secureCookies, retentionDays, getClientAddress})` is independent of environment variables and process user identity. The root HTTP server calls and awaits `handle(req, res)` before static routing, then calls `close()` during shutdown. API responses always use private/no-store and noindex headers. Storage must be a real persistent volume in production; the service does not decide whether a directory is a mounted volume.

The owner chooses the first password using a random setup token of at least 32 characters. The token travels in the URL fragment on the browser, is immediately removed there, and is posted in a JSON body. The database permits one owner only. Passwords use salted scrypt; sessions are random opaque cookies, stored only as SHA-256 hashes and expiring after 12 hours. Production cookies use the `__Host-` prefix, Secure, HttpOnly, Path=/ and SameSite=Strict. `secureCookies:false` is for local HTTP tests only.

Setup also generates eight independently random, single-use recovery codes with 192 bits of entropy each. The successful response is the only opportunity to see that set of codes; SQLite contains only SHA-256 digests of their canonical form. The browser may offer a local file download from the response held in memory. Codes must never enter a URL, browser storage, logs, analytics or a subsequent GET response. The setup token cannot be reused to reset an existing owner. A lost password can be recovered without email using an unused code. Losing both the password and every code prevents self-service recovery; this service does not provide email recovery or a backdoor.

The security API uses the following exact JSON contracts:

| Endpoint | Request | Success and session behavior |
| --- | --- | --- |
| `POST /api/owner/setup` | `{token,password}` | `{ok:true,recoveryCodes:string[]}`; creates the only owner and an authenticated session. |
| `GET /api/owner/session` | — | `{authenticated,configured}`; adds `recoveryConfigured:boolean` only when authenticated. Never returns a code or a code count. |
| `POST /api/owner/recovery-codes` | `{currentPassword}` | Authenticated and reauthenticated; `{ok:true,recoveryCodes:string[]}`. Replaces all previous codes atomically and retains existing sessions. |
| `POST /api/owner/recover` | `{recoveryCode,newPassword}` | `{ok:true}`. Consumes that code and updates the password in one transaction, revokes **all** sessions and clears the cookie. Sign-in is required afterwards. Other unused codes remain valid. |
| `POST /api/owner/password` | `{currentPassword,newPassword}` | Authenticated and reauthenticated; `{ok:true}`. Updates the password, revokes **all** sessions and clears the cookie. Sign-in is required afterwards. Unused recovery codes remain valid. |
| `POST /api/owner/backup` | `{currentPassword}` | Authenticated and reauthenticated; triggers the configured serialized backup scheduler and returns only verification time, integrity and retention metadata. Provider credentials and object keys are omitted; failure is generic. |

Passwords must contain 12–128 characters without control characters. Current-password proof, session validity and the unchanged stored password hash are checked again inside the security write transaction after asynchronous scrypt work. Login similarly rejects a password that changed while its scrypt check was running. A conditional delete inside an immediate transaction makes concurrent reuse of one recovery code succeed at most once. Invalid, consumed and unconfigured recovery attempts use the same generic error, without echoing a code or identifying an account. Codes may be pasted in their displayed form, in either letter case, or as the 48 hexadecimal characters without the `ELN-` prefix and separators.

All mutation requests require the configured exact Origin. Public bodies are bounded to 32 KiB. Interest records contain name, company, optional free-text ARR and email; enquiries contain comments and email. The website honeypot returns the same acknowledgement without storing the submission. No confirmation or marketing email is sent. No request bodies, passwords, email addresses or IP addresses are logged.

Public submission limits are 10 attempts per 15 minutes for each selected address, and 5 accepted attempts per hour for each case-folded email address. Setup has independent address and single-owner limits of 5 attempts per 15 minutes. Login and recovery each have independent address and single-owner limits of 8 attempts per 15 minutes. Password changes and code replacement share a further pair of 8-attempt address/principal limits, so switching security endpoints cannot bypass reauthentication throttles. Email and owner-principal limits are independent of forwarding headers. All rate keys are HMAC hashes held only in bounded process memory and reset on restart.

The default address selector uses the socket peer and ignores forwarding headers. Root may explicitly supply `getClientAddress(req)` for the specific Railway public-HTTP-edge deployment, selecting a validated singular `X-Real-IP` only when that deployment's ingress assumptions hold. No TCP proxy or untrusted direct/private ingress may be treated as that public edge. The selected address is an abuse signal, never an authorization boundary. Invalid selected addresses fall back to the socket peer. Railway documents the header at https://docs.railway.com/networking/public-networking/specs-and-limits#technical-specifications.

SQLite schema migrations run before serving; unknown newer schema versions fail closed. Version 2 adds the recovery-digest table while preserving version 1's owner, password hash, sessions and submissions. An existing owner can sign in normally, then create recovery codes by reentering the current password. WAL, full synchronous writes, foreign keys and secure deletion are enabled. Files use the provided path and standard SQLite siblings (`-wal`, `-shm`, and possibly `-journal`); known file symlinks are rejected. The root owns volume checks, ownership and dropping process privileges. Submission records are purged on startup and hourly after the configured retention period (365 days by default); unused recovery-code hashes remain until used or replaced. Delete and retention purge checkpoint the WAL after removing records. Any separately configured volume backups have their own retention policy and are outside this live-record service. Restoring an older whole-database backup can restore old credentials, sessions or previously consumed codes; a restore requires a separate owner-security procedure before reopening public access.

Only an authenticated owner can list, change status, delete or export. CSV fields are quoted, embedded quotes escaped and spreadsheet formula prefixes neutralised. The educational anonymous planner remains a separate browser-local store; it is not copied into this database.
